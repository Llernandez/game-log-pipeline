# 설계 결정

- 목표: 기대 결과를 정한 합성 데이터로 로그 재전송과 보상 중복 지급의 차이를 재현한다.
- RAW는 수신 단위, CLEAN은 event_id 단위, 거래는 player_id/currency/transaction_id 단위다.
- 같은 ID에 상충하는 데이터는 임의의 최신값으로 덮어쓰지 않고 모두 격리한다.
- reward_claim_id의 범위는 player_id/currency다. 다른 이용자가 같은 문자열을 썼다고 해서 중복 지급으로 보지 않는다.
- UTC로 표준화하고 event_time으로 일별 집계한다. ingested_at은 수집기가 별도 기록한다.
- 전체 원문 재계산을 기준 결과로 사용한다. 웨어하우스 작업은 기본적으로 증분이며, 새 입력과 이벤트·거래 키가 연결된 과거 행까지 다시 계산한다. 테스트에서는 각 입력 묶음의 증분 결과를 전체 재계산 결과와 비교한다. 이 설계는 원문 보존, 동일한 검증 규칙, 단일 로더의 커밋 순서를 전제로 한다. 병렬 적재의 정확성을 검증한 결과는 아니다.
- 이상 후보는 자동 제재가 아니다. 공개 정책은 시간당 360 demo_coin, 산정 시간 최대 2시간인 독립 가상 수치다.
- 입력은 허용된 필드 목록과 대조한다. 다만 검증 전 RAW에 원문이 저장되므로, 비공개 데이터는 수집 전에 차단해야 한다.
- Kafka exactly-once/커넥터 보장과 업무 단위 멱등성을 별도로 다룬다.
- 스키마 버전 변환은 재계산 단계에서 처리한다. RAW를 보존하고 각 버전을 공통 이벤트 형식으로 바꾼 뒤 검증한다. 같은 사건을 다른 버전으로 재전송한 경우 결과가 유지되는지 검사한다. 검증 규칙을 바꾼 경우에는 전체 재처리와 별도 대조 검사가 필요하다.
- 모니터링 설정(스크레이프 대상·경보·대시보드)은 코드와 같은 저장소에서 GitOps로 관리한다. 임계치는 데모 값이다.
- 게임 구현·캐릭터·경제·아트·저장·실제 로그는 이 저장소 밖에 둔다. 코드/아트에서 추출한 수치를 공개하지 않는다.

## 미해결 사항

- EKS values는 로더 3개를 지정하지만 증분 처리는 단일 로더를 전제로 한다. 실제 배포 전에 실행 수와 배포 중 중첩 실행을 제한하거나, 병렬 커밋에 맞게 처리 위치를 설계해야 한다.
- 보고서의 최상위 `source`는 고정값이다. 입력 출처별 건수와 합성 샘플 여부를 구분하는 보고가 필요하다.
- 단계 집계는 전체 관측 기록을 사용한다. 출처·게임 버전·관측 기간을 구분하지 않으며, 부분 로그에서 통과 기록이 없다고 실제 미통과로 단정하지 않는다.
